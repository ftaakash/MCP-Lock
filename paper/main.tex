\begin{abstract}
Coding agents usually launch Model Context Protocol (MCP) servers with commands like \code{npx -y pkg} that name no
version. Each launch can therefore fetch code nobody reviewed, along with new tool text that the model will follow as
instructions. In a census of \CensusSample{} MCP packages, \DriftPkgsP{} changed their advertised tools within 90 days,
and \NoSignalP{} of those changes came with no change in provenance, publisher or install scripts. MCP-Lock pins each
server's archive, build identity, publisher, install scripts and tool definitions in a lockfile, and a gate checks every
launch against that pin. In a pre-registered evaluation it detected \DetGP{} of \NR{} real attacks, against \DetSCP{}
for the closest earlier gate; \AblFour{} of its \AddedDet{} extra detections came from install-script diffs. Its false
blocks are inherited from the baseline's 30-day age rule. Dropping that rule for locked servers lowers them from \FbGP{}
to \AgeFbP, yet on fresh data, tested under a pre-registered addendum, the same change let \AoneLost{} of \AoneRC{}
hijacked packages through, so we leave it to the deployer. Against \ENCases{} attacks written with full knowledge
of the checks, the frozen gate let \EGAllow{} through. Five optional hardening switches bring this down to two, though
some of them block many honest upgrades; we report the cost of each on the \NB{} benign upgrades.
\end{abstract}

\section{Introduction}
MCP servers supply the tools of a language-model agent, and coding-agent harnesses mostly start them straight from a
package registry: \code{npx -y @scope/server}, \code{uvx server}. Unpinned launches are common: in the 2,660 agent
setups examined by Kapner et al.~\cite{kapner2026harness}, about one in ten (9.8\%) declared an MCP server without a
version. Such a launch takes whatever release is
newest at that moment. Between Monday's session and Tuesday's, the code may change, and so may the tool descriptions
that end up in the model's prompt. Those descriptions are a known injection channel~\cite{invariant2025poisoning}; a
server that alters them after approval is what the MCP literature calls a rug pull~\cite{invariant2025poisoning,hou2025mcp}.

Current defences miss this. The pre-install hook of Bagmar and Saraf~\cite{bagmar2026setup} looks at names, sources and
package age. Provenance (SLSA~\cite{slsa2023provenance}, Sigstore~\cite{newman2022sigstore}, PEP~740~\cite{pep740})
records who built an archive and says nothing about its tools, and the MCP registry does not version tool
definitions~\cite{kraishan2026drift}. Tools that pin the live tool list do exist~\cite{invariant2025mcpscan,mcppin,mcpseal},
but nobody has reported how often honest servers change their tools, or what a pin catches and costs.

Three questions guide the work. \textbf{RQ1:} how often do MCP servers change their tools, and does any
metadata signal show it? \textbf{RQ2} is about cost as much as benefit: does pinning provenance and tool definitions
catch more real attacks than the existing gate, and how many honest upgrades does it block on the way?
\textbf{RQ3} asks what an attacker would do if they knew every check.

\textbf{Contributions.} (i)~A census of MCP packages on npm and PyPI, with metadata for all \MetaPkgs{} eligible
packages and statically extracted tools for \CensusSample{} of them (Section~\ref{sec:census}). (ii)~MCP-Lock, a
lockfile and a gate that never runs package code (Section~\ref{sec:design}). (iii)~A pre-registered evaluation on real
malicious versions, synthetic rug pulls and benign upgrades, with a kill rule fixed in advance (Section~\ref{sec:eval}).
(iv)~An adaptive-attacker study with five hardening switches, each priced on benign upgrades (Section~\ref{sec:adaptive}).
Code, data and the registration are public.

\section{Background and Threat Model}
\label{sec:background}
An MCP client gets a server's tools by sending \code{tools/list}. For each tool the server returns a name, a
free-text description and a JSON schema for the arguments~\cite{mcpspec2025tools}, and all of it lands in the model's
context. Nothing fixes this list. A server can change it while running and simply send
\code{notifications/tools/list\_changed}, which is the opening a rug pull uses. On the
registry side, npm can attach a Sigstore-signed SLSA attestation naming the source repository, workflow and
builder~\cite{npmprovenance,slsa2023provenance,newman2022sigstore}, and PyPI does the same through PEP~740~\cite{pep740}.
npm also records, per version, the publishing account and the lifecycle scripts that run at install time. Stolen maintainer accounts and malicious
install scripts are old tricks~\cite{ohm2020backstabber,ladisa2023sok,zahan2022weak,zimmermann2019small}, and the 2025
Shai-Hulud worm used both at once~\cite{cisa2025shaihulud}.

\textbf{Threat model.} The developer runs a coding agent with our hook, and the lockfile was made while every
locked server was still benign. Some time later the attacker wants code to run, or text to reach the model, on a
launch. We split attackers into five tiers by what they control. A \emph{T1} attacker only registers a look-alike name.
\emph{T2} has one maintainer's stolen registry token, while \emph{T3} controls the release pipeline itself (the workflow,
or a merged commit). \emph{T4} owns the package, either malicious from the start or after buying it. \emph{T5} owns a
dependency. Registry compromise, forged Sigstore certificates and attacks on the model are left out.

\section{RQ1: Tool-Definition Drift}
\label{sec:census}
\textbf{Data.} Packages came from the official MCP registry and from MCP configuration files in public GitHub
repositories. To see a change at all we need two versions, so a package stayed in only if at least two of its versions
still resolve; \MetaPkgs{} did. We drew a random sample of \CensusSample{} from them, stratified by ecosystem and
download tercile with a fixed seed. Every version's archive was downloaded and checked against the registry digest.
Tool definitions were read from the source code, not from a running server: registration calls in JavaScript and
TypeScript, decorators or registration calls in Python. Some values are only known at run time. These become a fixed
placeholder, so the same source rebuilt later still gets the same hash (SHA-256 over the sorted, canonical
(name, description, schema) triples). Is static extraction good enough? We ran \ValN{} held-out servers in a container
without network and called \code{tools/list}. Tool-name precision was \ValPrec{} and recall \ValRec. High precision
means the changes we report are real; the lower recall means the drift figures below are, if anything, too small.

\textbf{Results.} Within a 90-day window, \DriftPkgsP{} \DriftPkgsCI{} of sampled packages (\DriftPkgs) changed their
tools. Restricted to packages with at least one release inside the window, the share is \DriftWinRelP{}
\DriftWinRelCI. Of all consecutive-version pairs where both sides had extractable tools, \DriftTransP{} (\DriftTrans)
differed: \KindAdded{} added a tool, \KindRemoved{} dropped one, \KindDesc{} edited a description and \KindSchema{}
edited a schema. Metadata did not reveal these changes. In \NoSignalP{} \NoSignalCI{} of tool-changing pairs, provenance,
publisher, maintainers and install scripts all stayed the same, and no one of these signals was more common on
tool-changing releases than on the rest (Fisher's exact test, four tests, all $p \ge \CoSignalMinP$). The signals
themselves are rare. Across \MetaTrans{} releases over twelve months, \MetaProvLostNpmP{} of active npm packages lost
provenance at least once, \MetaCiHumanP{} switched from CI to a human publisher and \MetaInstallNpmP{} gained an install
script; only \MetaLatestProvNpmP{} (npm) and \MetaLatestProvPyP{} (PyPI) of latest versions have provenance at all. Since tool changes happen often and these signals
rarely, a gate can only notice tool changes by comparing the tools.

\section{MCP-Lock Design}
\label{sec:design}
\textbf{Lockfile.} \code{mcp-lock.json} lives beside the harness configuration and holds one entry per server: exact
version, archive digest (npm SRI or PyPI SHA-256), build identity (repository, workflow, builder) if provenance exists,
npm publisher and maintainers, install scripts, and the canonical tool hash with tool names. Git ref and commit
are deliberately not part of the identity. Every honest release changes them, so including them would flag every
upgrade. An upgrade is accepted by regenerating the entry, and the user sees what changed as a diff.

\textbf{Gate.} It runs before the command. The gate parses install and runner commands such as \code{npx},
\code{pnpm dlx}, \code{bunx}, \code{uvx} and \code{pipx run}, resolves which version the command would fetch right
now, and compares that with the lock entry. Only registry metadata, attestations and archive contents are read; no
package code runs. Fig.~\ref{fig:arch} shows the flow. The checks are in Table~\ref{tab:signals}, with S1 a
re-implementation of the Bagmar and Saraf hook~\cite{bagmar2026setup}. A block denies the command and a warning asks the
user to confirm. We ship the gate as a Claude Code \code{PreToolUse} hook that sees both shell commands and edits to MCP
config files; if the gate itself fails, the user is asked.

\section{RQ2: Pre-Registered Evaluation}
\label{sec:eval}
\textbf{Design.} Before any scoring run we registered the hypotheses, corpora, scoring and a kill rule on
OSF~\cite{osf2026prereg} and froze the gate at a tagged commit. H1 says that on real attacks \G{} (S1--S5) detects more than \SC, the
stronger of two readings of the baseline. H2 says the two differ in false blocks on benign upgrades. If S2--S5 added
fewer than two detections and \G{} blocked honest upgrades at least as often, we would withdraw the method claim. Blocked
or warned counts as detected. Both hypotheses use exact McNemar tests~\cite{mcnemar1947} with Holm
correction~\cite{holm1979}, and rates come with Wilson 95\% intervals~\cite{wilson1927}. We logged six deviations from
the plan, each one before the affected results were seen; all concern replay mechanics or how the corpora were built.

\textbf{Corpora.} R-B holds the \NRB{} scenarios of the baseline paper. R-M has \NRM{} real malicious npm and PyPI
versions from the OpenSSF and Datadog datasets~\cite{ossfmalicious,datadogmalicious}. Most of them (\NRMC, class C)
hijack a package that already existed, and we lock each at its last clean version; the other \NRMN{} are new or
typosquatted names (class N). Together, R has
$n = \NR$. R-S, reported separately, has four classes of synthetic rug pull on 10 servers each plus 10 controls, all on
a local registry. B has \NB{} benign upgrades: \NBMcp{} MCP transitions from the census, \NBNpmTop{} from top npm
packages and \NBPyTop{} from top PyPI packages. Each case is replayed offline with the registry state of its
publication date. Malicious archives are read and never executed.

\textbf{Results.} Table~\ref{tab:rq2} has the numbers. H1 holds. H2 holds too, but against us: \G{} blocks
\FbDiffPP{} percentage points more honest upgrades than \SC. That cost is small, and the kill rule does not fire. Blocks
alone tell nearly the same story (\DetGBlockP{} vs.\ \DetSCBlockP). Taking S4 out of \G{} loses \AblFour{}
detections; S5, S3 and S2 account for \AblFive, \AblThree{} and \AblTwo. The gap is widest in class C, with \RMCGP{}
\RMCGCI{} for \G{} against \RMCSCP{} for \SC. Much of it traces back to install scripts added in the 2025 worm
campaigns~\cite{cisa2025shaihulud,checkpoint2025shaihulud}: by publication date, \WaveOneOnly{} and \WaveTwoOnly{} of
the \AddedDet{} extra detections fall in its two waves. Outside those weeks \G{} still detects \OutGP{} of \OutN{} R-M cases against \OutSCP{}
(\OutOnly{} vs.\ \OutSCOnly{} discordant, $p = \OutMcNemar$; exploratory). Class N is a tie at \RMNGP, all through the age
rule. S2 added nothing, and the reason lies in the data. Registries delete malicious versions after discovery, so S2
and S3 had something to compare in only \EvalSTwo{} of \NRM{} R-M cases, and only \STwoRMCP{} of class-C locks had
provenance in the first place. The synthetic rug pulls look very different: \G{} detects \RSG, \SC{} \RSSC, and no
control is flagged (\RSCtrl).

Most of what \G{} costs is review time. It blocks only \FbExtra{} more benign upgrades than \SC. S5 is the
expensive part: it warns on \WarnGP{} of B, nearly all of them MCP upgrades, where tools change often (RQ1). Per extra
detection that is \FbPerDet{} false blocks and \WarnPerDet{} warnings. We see the warnings as the more serious cost,
since a user warned on one upgrade in three may stop reading them. \SC's own \FbSCP{} false-block rate has another
source, the 30-day age rule applied again at upgrade time (\FbSCMcpP{} of MCP upgrades). Median latency is
\LatColdMed{}\,s on a cold cache (p95 \LatColdPNF{}\,s, $n = \LatN$) and \LatWarmMed{}\,s warm.

\textbf{Age rule (exploratory).} The 30-day rule protects the first use of a name, yet it also fires on each upgrade of
a young server the user has already locked, and that is where nearly every false block of \G{} comes from. Skipping it
for locked servers cuts false blocks from \FbGP{} to \AgeFbP{} \AgeFbCI. Detection on R falls by \AgeLost{} young hijacked
packages to \AgeDetP, which is still \AgeAdded{} above \SC. Because we picked this change after seeing the data, we filed
an OSF addendum and re-tested it on releases published after the freeze (9 Oct.--7 Nov.\ 2026): \AoneB{} benign upgrades
and \AoneR{} malicious versions, \AoneRC{} of them hijacks. The exempted gate \GX{} blocked \AoneFbGXP{} \AoneFbGXCI{} of
honest upgrades versus \AoneFbSCP{} for \SC{} ($p = \AoneHTwoP$), but detected \AoneDetGXP{} of attacks versus
\AoneDetSCP{} (\AoneHOneGX{} vs.\ \AoneLost{} discordant, $p = \AoneHOneP$). Every one of the \AoneLost{} misses was a
hijacked package under 30 days old that only the age rule had caught; just \AoneCEval{} of the \AoneRC{} hijacks still
had the registry data the other checks need. The registered rule demanded fewer false blocks with no loss of detection,
so the exemption is not confirmed. Exempting only packages older than $d$ days does not escape the trade-off either.

\section{RQ3: Adaptive Attacker}
\label{sec:adaptive}
For every tier we built the cheapest attack we could find against a gate whose checks, lock format and parser are
public. That gave \ENCases{} packages with harmless payloads on a local registry, plus \EElevenN{} command-line
variants of a single attack (Table~\ref{tab:matrix}). Every run used the frozen gate, and nothing was published or executed.

\textbf{What gets through.} \EGAllow{} of the \ENCases{} attacks pass the frozen gate; it blocks \EGBlock{} and
warns on \EGWarn. The largest blind spot is static extraction, which cannot see tools built at run time or pulled from
a URL (E6, E8b), and a remote-file rug pull does not even need a new release (E6b). Dependencies are another hole,
because the lock covers only the top-level archive (E9). A stolen token passes S2 and S3 when the lock never had
provenance (E2). And since the same-version check hashes only the locked file, an added file slips by (E10). Wrapping the launch in \code{npm exec}, \code{sh -c} or a shell variable hides it from the
parser. None of this is exotic: \ExpNoProvP{} of benign locks lack provenance, \ExpNonStaticP{} of versions keep their
tools out of reach of static extraction, and \ExpFloatSdkP{} of npm servers take their MCP SDK through a version range
(a lower bound, one dependency only). E4 cannot be fixed by any lock, because a payload released by the real pipeline
carries real provenance.

\textbf{Hardening (exploratory).} Five switches are off by default, and with all of them off a re-run of every corpus
reproduces the frozen results case for case. \emph{D1} locks the resolved npm dependency tree and runs S2--S4 on each
dependency whose version moved. \emph{D2} is a stdio proxy that pins each tool on first use, rejects a listing that adds
or changes a tool, and refuses calls to unpinned tools; because it checks every listing, it catches a time bomb when it
goes off. This is the design of the existing pinning proxies~\cite{mcppin,mcpseal}, here measured. \emph{D3} locks every
file of a PyPI release, \emph{D4} demands provenance and \emph{D5} normalises evasive command shapes. With all five on,
\EAllBlock{} of \ENCases{} attacks are blocked and \EElevenH{} of \EElevenN{} command shapes caught. E1 still only warns
and E4 still passes.

\textbf{Cost.} D3 and D5 cost nothing on B: D5 changed no decision (\HFive), and D3 only acts on a relaunch of the locked
version, though \HThreeLateP{} of locked PyPI releases did later gain a file. D1 newly blocks
\HOneBlockLateP--\HOneBlockEarlyP{} of npm upgrades, depending on when the lock was taken; a strict tree lock in the
style of \code{npm ci} would block \HOneStrictLateP--\HOneStrictEarlyP, so checking continuity rather than exact
versions is what makes D1 usable. D2 newly blocks \HTwoAddLoP--\HTwoAddHiP{} of benign upgrades, every one an MCP server
that changed its tools, and D4 \HFourAddP. D2's figure assumes the live tool list equals the static one, since an old
version cannot be observed without running it; \HTwoUnmeas{} upgrades with no static tools count as free.

\textbf{Suggestions (exploratory).} A block on its own leaves the agent guessing, and it may retry with something
worse. So the hook also suggests a replacement, but only one the gate itself accepts. A locked server gets the newest
acceptable version between lock and target, or the locked version if there is none; a typosquat gets the package it
imitates; a vulnerable pin gets the lowest release with the fix. For class C a
suggestion was offered in \SgRMCCov{} cases, and it was never the malicious version (\SgRMCBad).

\section{Discussion and Limitations}
\textbf{Main findings.} The confirmed gain over name-and-source checks rests mostly on install-script
diffs (S4), an old supply-chain signal with nothing MCP-specific about it. The age rule cuts both ways: re-applied to locked
servers, it makes both gates block about a third of honest upgrades, and it also catches young packages hijacked soon
after they were locked. On the new
data, dropping it for locked servers removed \AoneFbRemoved{} of \G's false blocks but missed \AoneLost{} of \AoneRC{}
hijacks. We would keep the rule by default, although a deployer with few young dependencies could reasonably decide
otherwise. S5 is what catches rug pulls, and RQ1 rules out a metadata shortcut. Its price is a warning on \WarnGMcpP{}
of honest MCP upgrades. Could S5 be narrowed? Of those \SfiveWarnN{} warnings, \SfDescP{} change a description,
\SfAddsP{} add a tool and \SfSchemaP{} only change a schema, which are the same edits a rug pull makes, so probably not
without losing the attacks it exists for. One caveat: no real attack in R is a known tool rug pull, so the case for S5
rests on R-S and RQ3. Provenance continuity is sound, but most packages have no provenance to compare.

\textbf{Limits of a lock.} A lock can only trust what was true when it was written. A T3 attacker releases through
the real pipeline, so the release looks honest, and a runtime pin compares only against the first listing it saw. The
gate turns change into a diff. Reading that diff is still a human job, and with S5 warning as often as it does, this is
probably the weakest point of the approach.

\textbf{Threats to validity.} A recall of \ValRec{} makes drift and S5 coverage lower bounds. R-M holds only
attacks that were caught and reported; whatever is still undetected is missing by definition. Replay cannot recover
deleted versions either, which explains the low S2/S3 evaluability. Class C rests on a simple rule (an earlier clean
version exists), so it may contain packages an attacker owned from day one. In the addendum at least \AoneOwned{} of
the \AoneLost{} misses look like that; without them, \AoneLostAdj{} misses remain ($p = \AoneLostAdjP$) and the
conclusion holds. We built the adaptive attacks ourselves, so a real attacker
may do better. Hardening, suggestions and the time-window split
were not pre-registered. D2's verdicts in Table~\ref{tab:matrix} come from tool lists read off each attack's source;
running the \RtCases{} locked servers offline in containers agreed in \RtAgree{} cases. D1 is a range because the time
of locking is unknown in practice.

\section{Conclusion}
Honest MCP servers change their tools often, and their metadata does not show it. Pinning archive, provenance,
publisher, install scripts and tools caught \AddedDet{} real attacks the existing gate missed, and the bill arrives
mostly as reviews of honest tool changes; on npm, adding \code{-{}-ignore-scripts} to the existing gate catches about
as many. An informed attacker gets past the frozen gate in \EGAllow{} of \ENCases{} attempts, and four of the five
hardening switches close most of the rest at a measured cost. Releases from a compromised pipeline and the review load
of honest change remain open problems for any lock.
